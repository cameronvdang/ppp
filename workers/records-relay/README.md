# FinchNode records relay

This stateless Cloudflare Worker supports **one owner using a dedicated FinchNode application**. Every caller with the relay token has that owner's access. A deployment serving independent users needs per-user authentication and session/subject ownership checks before live use. Exact browser Origin checks are an additional restriction, not authentication.

## Setup

1. Create a dedicated FinchNode application and enable the categories you intend to use: `demographics`, `medications`, `conditions`, `allergies`, `labs`, `vitals`, and `immunizations`. Other categories are rejected by this relay.
2. From the repository root run `pnpm install`, then `cd workers/records-relay`.
3. Configure `ALLOWED_ORIGINS` in `wrangler.toml` with the exact origins of your PPP app. Use commas for multiple origins, for example `https://your-app.example,http://localhost:5173`. Do not use wildcards, paths, trailing slashes, credentials, or prefix matching. A connection's return URL must match both the actual request Origin and an allowlist entry.
4. Save both required secrets interactively:

   ```sh
   pnpm exec wrangler secret put FINCHNODE_API_KEY
   pnpm exec wrangler secret put RELAY_CLIENT_TOKEN
   ```

   The first value is your server-side FinchNode application key. Use a high-entropy, unique relay token, such as one generated by `openssl rand -base64 32`. Keep both secrets out of source files, `[vars]`, browser code, and logs. `ck_test_placeholder` is an example value only.
5. Run `pnpm test`, then deploy with `pnpm deploy`.
6. Add your deployed relay's **exact origin** to the app's `connect-src` policy in `app/public/_headers`, or the equivalent configuration on your static host. In PPP Settings → Medical records, save its HTTPS URL and then its required relay client token. HTTP is accepted only for exact `localhost` or `127.0.0.1` development endpoints.
7. Open Records, select at least one category, consent, and choose **Connect my provider**. After Hosted Connect returns, PPP polls the stored session and imports the granted categories. Use **Refresh** for subsequent reads. Changing the saved relay URL disconnects live access, deletes the old bound token, and keeps the cached snapshot viewable. Save a new matching token before reconnecting.

For offline development, use `pnpm install --offline` with the pnpm store containing the locked dependencies. No live credentials or external requests are needed by the tests.

`FINCHNODE_BASE_URL` defaults to `https://api.finchnode.com/api/v1`. Overrides must identify that same HTTPS FinchNode contract endpoint; this Worker does not forward to arbitrary destinations. Neither secret belongs in `wrangler.toml` vars. Missing configuration returns 503; missing or incorrect tokens return 401 before any upstream call. Token digests are compared across all 32 SHA-256 bytes.

## Routes and limits

| Route | Behavior |
| --- | --- |
| `OPTIONS *` | Exact-origin preflight allowing `X-PPP-Relay-Token`. |
| `POST /v1/connect/sessions` | Accepts only `categories`, `returnUrl`, and a random 16–64 character `externalId`; adds one-time sync, 365-day duration and `Idempotency-Key: externalId`. |
| `GET /v1/connect/sessions/:id` | Validates the session ID and returns whitelisted session fields and validated sync metadata. |
| `GET /v1/users/:subject/records?categories=…` | Validates the subject and one nonempty, unique, supported category list, then streams JSON. |

Both category routes reject empty, duplicate, malformed, or unsupported category selections. Input bodies are limited to 16 KiB and five seconds, including streamed bodies without Content-Length. Upstream requests and response reading have a ten-second deadline. The Worker uses omitted credentials, no-store caching, and rejected redirects upstream. It forwards complete error envelopes while sanitizing local failures and credential echoes. Responses include `Cache-Control: private, no-store`, `Vary: Origin`, and browser-visible `Retry-After` and `RateLimit-Limit/Remaining/Reset` headers.

## What the relay can and cannot see

The trusted operator can see subject IDs and record bodies in transit. The Worker stores nothing: there is no KV, R2, hosted records database, or application body logging. It cannot read PPP's local vault, encryption key, or browser history. It is separate from the opt-in encrypted backup relay, which stores encrypted backup uploads.

FinchNode and the connected source provide their own authorization and consent receipts. Disconnect and delete clears PPP's local records and declines its local records consent. To revoke access at the source, use the provider's portal or FinchNode's consent controls too. See [PRIVACY.md](../../PRIVACY.md) for the complete app privacy boundary.
